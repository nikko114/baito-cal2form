# baito-cal2form 計画書

- 状態: ドラフト（§11 の質問の回答待ち。回答を反映して更新する）
- 最終更新: 2026-10-17

カレンダーでシフト希望を入力すると、Googleフォームに書き写すための一覧ができるスマホ向けWebアプリ。

## 1. 目的

- シフト提出のGoogleフォームは「1日ごとにプルダウンで選ぶ」形式。日付・曜日・自分の予定の対応がつかみにくく、選び間違えやすい。
- 曜日の見えるカレンダーの上で希望を決め、フォームと同じ文言で1日1行の一覧を作る。フォームへの入力は、一覧を上から順に見ながら選ぶだけにする。

## 2. 使い方の流れ

1. **初回だけ**: 設定画面で、フォームのプルダウンにある選択肢をフォームと同じ文言・同じ順番で登録する。カレンダー用の短い表示名と色もつける。
2. **毎回**: カレンダーで日付ごとに選択肢を選ぶ。
3. **提出するとき**: 一覧画面で提出期間を選ぶと、`11/1(土) 終日OK` のような一覧ができる。未入力の日は赤く表示して警告する。
4. 一覧を見ながらフォームに入力する。入力し終えた行をタップして✓をつけていけば、アプリとフォームを行き来してもどこまで入れたか見失わない。

## 3. 画面と機能（MVP）

画面下のタブで3つの画面を切り替える: **カレンダー / 一覧 / 設定**。スマホ優先で作り、PCで開いても崩れないようにする。

### 3.1 カレンダー（メイン画面）

- 1か月表示（7列）。前月・次月に切り替えられる。今日と土日は色を変える。
- 各日のマスに、日付と選んだ選択肢の短い表示名を色つきで出す。
- **タップ入力**: 日付をタップすると、下から選択肢のボタンが出る。選ぶと保存して**自動で翌日に進む**（シートは開いたまま。月をまたぐと表示も切り替わる）。シート上部に「◀ 日付 ▶」と閉じるボタンを置く。1日1タップで順番に埋められる。
- **塗りモード**: 画面下のパレットで選択肢を選んでから日付をタップして塗る。同じ選択肢が入っている日をもう一度タップすると未入力に戻す。曜日の見出しをタップすると、表示中の月の同じ曜日をまとめて塗る（「火曜は全部×」など）。
- **元に戻す**: 直前の操作を取り消す（まとめ塗りの間違い対策）。
- 一覧画面で選んだ提出期間の外にある日は薄く表示する。

### 3.2 一覧（出力）

- 期間は開始日〜終了日で指定する。プリセットは「来月 / 今月 / 1〜15日 / 16日〜月末」。前回の期間を覚えておく。
- 期間内の全日を1日1行で表示する（例: `11/1(土) 終日OK`）。週の区切りには線を入れる。
- 未入力の日は赤く表示し、件数を画面上部に出す。タップするとカレンダーのその日に飛ぶ。
- 日付の書き方はフォームに合わせて選べる: `11/1(土)` / `11月1日(土)` / `1日(土)`。
- **コピー**ボタン（プレーンテキスト）。
- **チェックリスト**: 行をタップすると✓がついてグレーになる。進み具合（12/30 など）を表示し、✓の状態は保存する。画面に戻ってきたら、次の未チェックの行まで自動でスクロールする。リセットボタンもつける。

### 3.3 設定

- 選択肢の追加・編集・削除・並べ替え（↑↓ボタン）。各選択肢に持たせるもの:
  - **フォームの文言**: 一覧に出す文字列。フォームと一字一句そろえる。
  - **短い表示名**: カレンダーのマス用の2〜3文字。初期値は文言の先頭から自動で作る。
  - **色**: 10色程度のパレットから選ぶ。
- まとめて追加: 1行に1項目ずつ書いて一括登録する。
- 使っている日がある選択肢を削除するときは「◯日で使われています」と確認し、その日は未入力に戻す。
- 未入力の日の扱い: 警告だけ（初期値） / 指定した選択肢で埋める（例: 未入力は「×」とみなす）。
- 週の始まり: 日曜（初期値） / 月曜。
- バックアップ: 書き出し（クリップボードにコピー、またはファイル保存）と読み込み。
- 全データ削除。

## 4. データ設計

ブラウザの localStorage に、キー1つでJSONをまとめて保存する。1年使っても数十KB程度に収まる。

```ts
type ShiftOption = {
  id: string; // 変わらないID。日付の側はこのIDで選択肢を参照する
  label: string; // フォームの選択肢と同じ文言（一覧に出す）
  short: string; // カレンダー表示用
  color: string;
};

type AppData = {
  version: 1; // データ形式を変えるときの移行用
  options: ShiftOption[]; // 配列の順番 = フォームでの順番
  entries: Record<string, string>; // "2026-11-01" -> ShiftOption.id
  checked: Record<string, true>; // チェックリストの✓（キーは日付）
  settings: {
    weekStartsOn: 0 | 1;
    dateFormat: "M/D(W)" | "M月D日(W)" | "D日(W)";
    unsetFill: string | null; // null = 警告だけ / optionId = その選択肢で埋める
    lastRange: { start: string; end: string } | null;
  };
};
```

- 日付は Date オブジェクトではなく `"YYYY-MM-DD"`（端末のローカル日付）の文字列で持つ。
- 日付からは選択肢をIDで参照するので、選択肢の文言を直すと、登録済みの日にもそのまま反映される。
- 読み込むときに形式をチェックし、壊れたデータや別物のバックアップを読み込んでもアプリが落ちないようにする。

## 5. 技術構成（提案）

| 項目 | 選択 | 理由 |
| --- | --- | --- |
| ビルド | Vite | 設定が少なく速い |
| 言語・UI | TypeScript + React | 定番で情報が多い。画面の状態の扱いが楽 |
| 状態管理 | useReducer + Context | この規模なら外部ライブラリは不要 |
| スタイル | 素のCSS（CSS Modules）。スマホ優先 | 依存を増やさない |
| 日付処理 | 自前の小さなユーティリティ | 必要な処理が少ない |
| テスト | Vitest（ロジック）。Playwright（スマホ幅で主要な流れだけ） | |
| 公開 | GitHub Pages（GitHub Actions で自動デプロイ） | リポジトリが公開なので無料。HTTPS になる（コピー機能に必要） |
| PWA | Web App Manifest + Service Worker（vite-plugin-pwa） | ホーム画面に追加でき、オフラインでも動く。iPhone のデータ消去対策にもなる（§9） |

- サーバーなし、外部との通信なし。データは端末のブラウザの中にだけ残る。
- 開発の流れ: main に直接 push → Actions でテストとビルド → 通れば Pages に反映。テストが落ちたら公開中の版はそのまま残る。
- 公開URL（予定）: https://nikko114.github.io/baito-cal2form/
- 初回だけ、リポジトリの Settings → Pages で Source を「GitHub Actions」にする操作が必要（Actions の標準の権限では有効化できないため）。

## 7. MVPのあとの候補

- 曜日ごとの初期値（「毎週火曜は×」を一度設定すれば毎月自動で入る）
- 祝日の表示
- 曜日によって選べる選択肢を変える（平日と土日で選択肢が違うフォーム向け）
- 複数のバイト先（設定のセットを切り替える）
- 一覧に、フォームでの並び順（何番目の選択肢か）を出す

## 8. 発展案: 事前入力URLで「ポチポチ」自体をなくす

Googleフォームには、URLで回答を先に入れておく仕組み（事前入力URL）がある。

```
https://docs.google.com/forms/d/e/<フォームID>/viewform?usp=pp_url&entry.123456=終日OK&entry.234567=×
```

各日付の質問のID（`entry.数字`）がわかれば、全日分の答えが選ばれた状態でフォームを開くURLを作れる。あとは中身を確かめて送信ボタンを押すだけになる。

- **IDの手に入れ方**: 回答者の側からでも、フォームのページに埋め込まれた質問データ（`FB_PUBLIC_LOAD_DATA_`）から取り出せる。
  - 例: PCでフォームのページのソースを開いて全部コピーし、このツールに貼り付ける。ツールが質問タイトル・ID・選択肢を読み取り、日付と結びつける。プルダウンの選択肢も設定にそのまま取り込める。
  - フォームのページで実行するとデータをコピーするブックマークレットを用意する手もある（スマホだとブックマークレットの登録が少し面倒）。
  - アプリからフォームを直接読みに行くことは CORS の制限でできない。やるならサーバーが必要になるので、今回はやらない。
- **向いているケース**:
  - フォームが毎回同じもの（使い回し）なら、最初に1回設定するだけで済むので効果が大きい。
  - 毎回新しいフォームが配られるなら、そのたびにソースを貼り付ける必要がある（PCなら数十秒。スマホだけだと面倒）。
- **注意**:
  - 選択肢の文言が完全に一致しない質問は空欄のまま開く。
  - ログインが必要なフォームでもうまく動くかは、実物で確かめる必要がある。
  - 埋め込みデータの形式は Google が公開している仕様ではないので、変わる可能性がある。
- **進め方**: MVPのあと、実際のフォームで試してから入れるかどうか決める。

## 9. 注意点・リスク

- **iPhone の Safari ではデータが消えることがある**: Safari は、しばらく操作していないサイトの保存データを消す（Safari を使った日で数えて7日。ITP という仕組み）。月1回しか開かない使い方だと、シフトや設定が消えるおそれがある。
  - 対策1: **ホーム画面に追加**して使ってもらう。ホーム画面に追加したWebアプリはこの削除の対象外。アプリ内で追加を案内する。
  - 対策2: バックアップの書き出し機能（ホーム画面版でも消えたという報告が過去にあるので、念のため）。
  - 注意: Safari とホーム画面版は保存場所が別。Safari で入れたデータはホーム画面版に引き継がれないので、移すときはバックアップを使う。
- **日付のずれ**: JavaScript の `toISOString()` は UTC で返すので、日本時間の0時が前日の日付になる。日付は必ずローカルの日付で扱い、テストで確かめる。
- **スマホ表示の細かい落とし穴**: iOS の `100vh` 問題（`100dvh` を使う）、画面下のホームバーとの重なり（safe-area）、16px未満の入力欄にフォーカスしたときの自動ズーム、ダブルタップでのズーム（`touch-action: manipulation`）。
- **動作確認の限界**: 開発環境で自動テストできるのは Chromium だけ。Safari 特有の動きは実機で確認してもらう必要がある。

## 10. やらないこと

- サーバー、アカウント、端末間の同期
- 確定したシフトの管理、給料の計算
- Googleカレンダーなど外部カレンダーとの連携
- フォームの自動送信（送信ボタンは必ず自分で押す）

## 11. 未確定事項（質問）

### 回答がほしいこと

1. フォームの中身（スクリーンショットがあれば一番助かる。名前などは隠してOK）
   - 質問タイトルでの日付の書き方（`11/1(土)`、`11月1日`、`1日` など）
   - 1回のフォームで何日分か（1か月 / 半月 / 1週間）
   - プルダウンの選択肢の一覧。全部の日で同じか（平日と土日で違わないか）
   - 1日あたりのプルダウンは1個か（開始時刻と終了時刻で2個、などではないか）
   - 日付以外の質問（名前、希望日数、備考など）はあるか
2. 使っているスマホは iPhone か Android か。フォームはそのスマホで入力するのか、PCで入力するのか
3. フォームは毎回同じURL（使い回し）か、毎回新しいものが配られるか。§8 の事前入力URLに興味はあるか
4. 「毎週◯曜は授業で無理」のような決まったパターンはあるか（あれば曜日ごとの初期値をMVPに入れる）

### 希望がなければ次の内容で進める

- 未入力の日は警告だけにする（設定で「×で埋める」に切り替えられる）
- 週の始まりは日曜
- 技術は Vite + React + TypeScript。GitHub Pages で公開する
- 祝日の表示と複数のバイト先への対応は MVP のあと
- 自分専用で使う想定（バイト仲間にも配るなら、選択肢の設定を共有する機能を検討する）
